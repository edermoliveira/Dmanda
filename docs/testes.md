# Testes do Dmanda

Guia das suítes em `scripts/`. A lista curta de comandos está no `CLAUDE.md`; aqui ficam as convenções, as portas, o esqueleto de uma suíte nova e, no fim, as descrições detalhadas de cada suíte como estavam no `CLAUDE.md` até 19/11/2026.

Estes testes validam a lógica e a interface no banco de **teste** (PGlite), com dados fictícios. Não substituem a validação no Supabase real, que se faz com a CLI oficial (`npx supabase db query --linked`, `db push --linked --dry-run`, `db advisors --linked`), só neste projeto, sem `db reset` e com transações desfeitas nos testes que não podem deixar dados. O WebKit do Playwright é o motor do Safari no Windows, **não** o Safari do aparelho.

## Convenções (cada uma tem um lugar só)

| O quê | Onde fica |
|---|---|
| Servidor de teste (`next dev` com `DMANDA_BANCO=teste`), espera, parada, repetição da partida **só** quando o Next responde e cai logo depois (aviso de atualização); saída antes de responder, porta ocupada e servidor mudo dão erro claro na hora | `iniciarServidor` e `pararServidores` em `scripts/auxiliar-navegador.mjs` (os caminhos negativos são provados em `testar:auxiliar`) |
| Edge, WebKit, contexto com relógio e tema, erros de página e de console, contador de verificações (`ok`, `aguardar`, `resumo`) | `scripts/auxiliar-navegador.mjs` |
| Titular de teste (`USUARIO_TESTE`, e-mail autorizado) | `src/servidor/banco-teste-base.mjs` (o servidor de desenvolvimento e as suítes usam o mesmo) |
| Sementes de dados fictícios | `scripts/semear-agenda.mjs`, `semear-volume.mjs`, `auxiliar-origem.mjs`, `auxiliar-retorno.mjs` |
| Operações que o código pede ao banco x lista fixa de `executar_como_titular` | `scripts/auxiliar-operacoes.mjs` (cobrado em `testar:regras` e usado em `testar:acesso-direto`) |
| Segredo da rotina diária nos servidores de teste | `SEGREDO_CRON_TESTE`; só as suítes que chamam a rota (`testar:app`) pedem `cron: true` |

- Um `next dev` por vez: a pasta `.next` tem trava. As suítes rodam em sequência, nunca em paralelo.
- A pasta de dados de cada suíte fica em `.dados-teste/<nome>` (ignorada pelo Git, apagada no início da execução).
- `verificador.aguardar(waitFor..., mensagem)` é uma verificação por espera: se o tempo estoura, aparece como "FALHOU" (e não derruba o script sem o resumo). Use `ok(condição, mensagem)` quando houver uma condição a medir.
- Cada suíte tem a sua porta (`PORTA_TESTE_<NOME>` muda a padrão); `testar:regras` falha se duas repetirem uma.

## Esqueleto de uma suíte de navegador

```js
import { rmSync, mkdirSync } from 'node:fs';
import { abrirEdge, criarVerificador, iniciarServidor, novoContexto, semearBanco } from './auxiliar-navegador.mjs';

const PORTA = process.env.PORTA_TESTE_NOVA || '71xx', BASE = `http://localhost:${PORTA}`, PASTA = '.dados-teste/nova';   // uma porta que nenhuma outra suíte use
rmSync(PASTA, { recursive: true, force: true }); mkdirSync('.dados-teste', { recursive: true });
await semearBanco(PASTA, async (chamar) => { await chamar('criar_demanda', { p: { assunto: 'Exemplo', tipo: 'Memorando' } }); });   // antes do servidor: o PGlite de uma pasta não é compartilhado
const { parar } = await iniciarServidor({ porta: PORTA, pasta: PASTA });
const { ok, aguardar, resumo } = criarVerificador();
const nav = await abrirEdge(), erros = [];
const { ctx, pg } = await novoContexto(nav, { opcoes: { viewport: { width: 1360, height: 900 } }, erros });
await pg.goto(BASE + '/');
// ... ok(condição, 'mensagem'); await aguardar(pg.waitForSelector('...'), 'mensagem');
ok(erros.length === 0, 'nenhum erro de página nem de console');
await ctx.close(); await nav.close(); parar();
process.exit(resumo());
```

## Convenções novas (decisão 92)

- **Identidade nas suítes de navegador:** o servidor de teste (`iniciarServidor`) define `DMANDA_USUARIO_TESTE` (a conta de teste autorizada e não administradora); não há tela de entrada em modo de teste. Para agir como a administradora de teste, um contexto usa o cookie `dmanda-teste-usuario` com o id de `ADMIN_TESTE`. A integração real (cookies, proxy, renovação) é só do `testar:auth-fluxo`.
- **Rascunhos online:** o servidor de teste limpa os rascunhos ao subir (`/api/teste/rascunhos`, só em modo de teste). Para ler os rascunhos de uma página use `rascunhosDaConta(pg)` (banco pela exportação mais a fila local pendente); para injetar um rascunho pendente use `filaComPendentes` e `CHAVE_FILA_TESTE`. O que o banco confirmou NÃO fica no armazenamento do navegador, então não se confere rascunho lendo `localStorage` direto.
- **Interceptação de rede:** os rascunhos vão por `/api/rascunhos` (fetch), fora das ações do servidor; interceptar `next-action` não os alcança.
- **Prévia de avaliação da autenticação:** `npm run previa:auth` sobe o aplicativo em modo real na 7100 (também pelo IP da rede) contra o Auth fictício na 7149 (`/caixa` mostra os convites e as recuperações fictícios, com o link). Contas e senhas fictícias impressas ao subir e gravadas em `%TEMP%\dmanda-previa-auth\LEIA.txt`. Ocupa a pasta `.next`: encerre-a antes de rodar suítes de navegador.
- **`testar:auth-fluxo` (80 verificações em 22/11; inclui a primeira leitura de rascunhos atrasada além do limite):** também cobre a etapa de senha (assinatura, usuário, sessão, uso único, cookie forjado, etapa de outra conta, finalidade trocada na URL), a troca da própria senha com sessão antiga e a recusa do Auth fictício a uma sessão antiga sem reautenticação, a revogação com a página aberta (tela de acesso revogado, fila guardada com a dona e sem reenvio), a troca de conta por baixo de uma página aberta e o formulário de login POST desativado até a hidratação.
